## CRITICAL RULE: Determine the correct answer before writing the final question

When a question involves code, calculations, or logical evaluation:

1. Decide exactly what concept is being assessed.
2. Finalize any code, expressions, scenario, or conditions needed by the question.
3. Solve the problem completely.
4. Double-check the result.
5. Only then construct distractors.
6. Verify every distractor against the FINAL version of the question.
7. Only after all of this should you write the final JSON.

If you discover an error while designing or verifying a question, discard or reconstruct the affected question rather than patching inconsistent values.

Perform all planning, solving, and verification internally. Do NOT output your internal planning or reasoning.

## DIFFICULTY CALIBRATION

Use the supplied reference examples as the primary local guide for what the requested difficulty looks like for this topic.

Also use these general definitions:

### D1 — Easy

Direct application or recognition of a concept.

Usually requires one main reasoning step and little or no synthesis.

### D2 — Medium

Requires multiple reasoning steps or coordination of more than one aspect of the target concept.

May involve tracing, comparison, interpretation, application in a less direct setting, or distinguishing among several plausible choices.

### D3 — Hard

Requires sustained multi-step reasoning, synthesis, backward reasoning, careful comparison of plausible alternatives, or interaction among several aspects of the target concept.

The difficulty should come primarily from reasoning, not merely from longer code, more variables, more arithmetic, or a longer explanation.

Before accepting each question, compare it with the supplied examples and ask internally:

"Would this question require an appropriate amount of reasoning from a well-prepared AP CSA student for the requested difficulty?"

If not, revise it.

## TOPIC FIDELITY

The Target Topic(s) define what the question should actually assess, not merely what vocabulary or syntax may appear in it.

A question may use ordinary prerequisite knowledge, but the knowledge REQUIRED to determine the correct answer must primarily belong to the specified Target Topic(s).

Do not make a question difficult by introducing unrelated Java rules, APIs, syntax details, or concepts from other topics unless they are necessary prerequisites or explicitly included in the target topics.

Before accepting a question, ask internally:

"If a student understands the target topic well but has not yet studied a later or unrelated topic, could that unrelated knowledge determine whether they get this question correct?"

If YES, redesign the question so that the target topic remains the primary source of difficulty.

## FORM FIDELITY — CRITICAL

Each new question is assigned a form-model example (see Target). The form of a question is:

- the kind of task the student does (for example: determine an output, choose code that works, identify an error, choose a missing expression, choose a true statement)
- how the stem is laid out (for example: code segment then question, method with a blank, a described goal and no code)
- the answer-choice format: single values, short expressions, one-line statements or sentences, or multi-line code blocks
- the approximate length of the stem and of each answer choice

Match all of these to the form-model example. In particular:

- If the form model's answer choices are single values, expressions, or one-line statements, yours must be too. Do NOT turn them into code blocks.
- Use multi-line code blocks as answer choices ONLY if the form model does, and keep them about as long as its choices.
- Do not switch to a different kind of task because it seems more interesting or more varied.

Variety comes from the content: a different skill within the target topic, different code, a different scenario. It does not come from inventing a form that the examples do not use.

Copy the form, NOT the setup or the wording:

- Use different data, different variable and method names, and a different algorithm or traversal from the form model. For example, if the form model fills an `ArrayList` named `result` from `mat` and states what `result` should contain, do not build your question around an `ArrayList` named `result` filled from a 2D array.
- Write your own sentences. Reuse the form model's wording only for the standard question line (for example "Which of the following can replace `/* missing code */` ..."), and do not copy explanatory sentences or notes from its stem.
- If the form model contains a grammar or typing error, do not reproduce it.
- A student who has seen the form model should not recognize your question as the same question with new numbers.

If the form model's task genuinely cannot assess the assigned subtopic at the requested difficulty, use the form of another reference example instead. Never use a form that none of the examples use.

If no examples are provided, keep answer choices short (values, expressions, or one-line statements) unless the task itself requires choosing between code segments.

Questions listed under "Questions Already in This Set" may share a form with the new question. That is fine. They must not share the same skill with only the values changed.

## INTERNAL WORKFLOW

Perform the following steps internally for the entire batch.

Do NOT output these steps.

### Step 1: Form Plan

For each question:

- look at its form-model example and note its task, stem layout, answer-choice format, and lengths
- decide the specific skill within the target topic
- decide the reasoning required
- confirm the skill differs from the other new questions and from any questions already in the set

---

### Step 2: Plan and Solve Each Question

For each question:

- determine exactly what is being tested
- construct the FINAL version of any code, expressions, scenario, conditions, or answer alternatives
- solve the question completely
- independently verify the correct answer

Use the solving method appropriate to the assessment structure.

For example:

**Value-trace question:**
Trace the code step-by-step and determine the final value, state, or output.

**Code-selection question:**
Evaluate every proposed code segment and verify exactly which one satisfies the stated goal.

**Algorithm-selection question:**
Determine the required relationship or behavior and verify each proposed procedure.

**Equivalence question:**
Reason about every relevant expression or code segment and verify whether equivalence holds under the conditions stated in the stem.

**Error-analysis question:**
Identify the precise erroneous assumption, operation, or statement and verify the correction.

**Modification question:**
Determine the desired result first, then verify which proposed modification actually produces it.

Do not force every question into a code-tracing workflow.

---

### Step 3: Design Distractors

Only after the question and correct answer are fully finalized:

- identify specific realistic student misconceptions
- construct each distractor from one of those misconceptions
- apply the misconception to the EXACT final version of the question
- recompute any resulting values from scratch
- verify that the distractor really follows from the stated misconception
- verify that the distractor is actually incorrect for the stem AS WRITTEN
- verify that its explanation accurately describes why it is incorrect

Distractors may represent errors such as:

- misunderstanding operator behavior
- incorrect precedence or associativity
- off-by-one errors
- wrong loop bounds
- pass-by-value confusion
- incorrect state tracking
- incorrect method behavior
- confusing related concepts
- choosing code that works in some cases but not under the conditions in the stem
- plausible arithmetic or logical mistakes

Use misconceptions appropriate to the actual target topic. Every distractor must exercise the target topic: for example, in a recursion question a non-recursive option is not a useful distractor.

Do not use arbitrary values merely to fill answer slots.

If no realistic misconception produces a distractor, say what that choice computes or does and why it differs from the correct answer. Do not invent a misconception to explain it.

---

### Step 4: Final Verification

Before returning the batch, verify ALL of the following:

- exactly `{count}` questions are present
- each question contains exactly 5 answer choices
- exactly ONE answer is correct for each question
- every answer choice has been independently evaluated
- every answer marked incorrect is actually incorrect for the stem AS WRITTEN
- every question primarily assesses the specified target topic(s)
- each question matches its form-model example's task, stem layout, answer-choice format, and approximate lengths
- each question reasonably matches the requested difficulty
- every distractor explanation matches the actual choice (see Step 3)
- every correct-answer explanation is accurate
- the overall explanation agrees with the marked correct answer
- every factual statement about Java behavior is correct
- all Java code is syntactically valid
- all calculations are correct
- all inline code references are wrapped in backticks
- Java code blocks use `java`
- every method, class, table, or data set the stem refers to (for example "the following method") is actually shown in the stem
- answer choices are code blocks only if the form-model example's choices are; when they are, they are fenced `java` blocks laid out over several lines, not one-line inline code
- code in the question stem contains no comments that reveal computation steps, intermediate values, or the solution path
- the generated questions use different code, values, wording, and scenarios from the examples, and do not reuse the form model's setup (its data structures, variable names, or explanatory sentences)

A contextual comment such as `// ASCII value 65` may be acceptable when it merely supplies necessary background.

A comment such as `// x becomes 7`, `// evaluates to 12`, or `// integer division gives 4` is NOT acceptable because it performs part of the student's reasoning.

If any check fails, silently revise the affected question before producing the final output.

## Field Guidelines

- `text`
  - Complete question text in markdown format.
  - May include Java code in fenced `java` blocks.

- `answers`
  - Exactly 5 answer choices.
  - Exactly one answer must contain `"is_correct": true`.
  - Every answer must contain an `explanation`.

- answer `text`
  - Use backticks for inline code such as `42`, `count`, or `arr[i]`.
  - Use fenced `java` blocks for multi-line Java code.

- answer `explanation`
  - Briefly explain why that specific answer is correct or incorrect.
  - Explanations for distractors must accurately identify the misconception represented by the choice.

- `explanation`
  - Students read this field. Write it as a teacher explaining the solution, not as a question writer.
  - Provide a clear walkthrough or justification for the correct answer.
  - Include intermediate reasoning where appropriate.
  - Do NOT include question-design notes: no "Plan & Solve", "Design Distractors", "Distractor B", verification checkmarks, or commentary about how the question was built.
  - Do NOT refer to answer choices by letter or position (A–E, "the first option"). Choices are shuffled when displayed, so refer to a choice by its content, e.g. `"Fundals"`.

- `difficulty`
  - Use the requested difficulty ID only, e.g. `"D2"`.

- `cognitive_level`
  - The Bloom's level the question actually demands. Pick exactly one:
    - `B1` Remember: recall a fact or rule
    - `B2` Understand: explain or interpret a concept
    - `B3` Apply: use a rule or procedure in a new situation (e.g. trace code)
    - `B4` Analyze: compare alternatives, find errors, reason about structure or equivalence
    - `B5` Evaluate: judge which approach is best or justify a decision
    - `B6` Create: design or construct something new
  - Use the reference examples to calibrate. Do not default to `B3`.

- `topics`
  - Use exactly the topic codes given in the Output Format: `{topic_ids}`.

- `subtopics`
  - The ID(s) of the subtopic(s) the question assesses, chosen from the Subtopics of the Target Topic(s) list, e.g. `["ST007"]`.
  - If an assigned subtopic is given, use exactly that ID.
  - If no subtopic list is given, use `[]`.
